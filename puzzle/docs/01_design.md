## 1. ゲームルール（Bus Jam型：「おまちどう」行列整理モード）【確定・実装済み】

寿司屋のテーマで説明する。ルール本体はテーマと無関係（§6）で、「バス」テーマに差し替えても同じルールで遊べる。

### 1.1 構成要素

| 要素 | 内容 |
|---|---|
| 待合（盤面） | W×H のマス目。各マスは「空き」「客」「柱（通れない）」のどれか。上辺がカウンターへの出口 |
| 客 | ネタの色（=注文）を1つ持つ。各ネタの客数は必ず3の倍数 |
| カウンター | いま握っている皿が1枚。皿には**3席**あり、同じネタの客だけが座れる |
| 皿の列 | これから出る皿の順番。**全件を常に表示** |
| 待ち席 | 合わない客を一時的に座らせる長椅子。席数 K（標準5、21〜30面などは4）。**K 席目が埋まったら負け** |

### 1.2 操作と処理（タップのみ）

1. 客をタップする。その客から**上辺の出口まで、空きマスだけを通る上下左右の道**があれば動ける（いちばん上の行の客は常に動ける）。道が無い客は少し揺れるだけで何も起きない。
2. 動ける客は：
   - 注文が**いまの皿と同じ** → カウンターの空席へ座る
   - 違う → 待ち席へ
3. 皿の3席が埋まると、客が食べ終えて皿が下がり、次の皿が出る。
4. 新しい皿と同じ注文の客が待ち席にいれば、**自動で**カウンターへ移る（左から順）。これで皿が埋まれば、さらに次の皿へ進む——**連鎖**。
5. 客が抜けたマスは空きになり、奥の客の道が開く。

### 1.3 クリアと失敗

- **クリア**：全員が食べ終える（皿の列が空になる）。
- **満席（失敗）**：待ち席がすべて埋まった。残り1席になると待ち席が赤くなり「あと1人で満席」と表示する。
- **手詰まり（失敗）**：動かせる客が1人もいない（予約札やのれんの配置で起こりうる）。もうクリアできない局面になっても、手が残っている間は知らせない。
- 手数制限・時間制限は無い。失敗画面からは「最初からやり直す」（無料・無制限）。一手戻すは無い。

### 1.4 このルールで生まれる考えどころ

- どの客を先に出すと、奥の客の道が開くか（盤面整理）
- 待ち席の何席までなら使ってよいか、何を預けると後の皿で一気に連鎖するか（効率・連鎖）
- 皿の列を先読みし、待ち席が残り1席の状況から立て直す（ギリギリからの逆転）

### 1.5 ギミック【実装済み】

すべて**見た目で状態が分かる**もの。隠し情報・時間で変わるものは採用しない。導入面では説明を表示し、小さめの盤面で単独に使ってから組み合わせる。

| ステージ | 追加要素 | ルール |
|---|---|---|
| 1〜10 | 基本 | 2色・3×4 から 5色・6×6 まで |
| 11〜20 | 柱 | 通れないマス |
| 21〜30 | 待ち席4席 | 4席目が埋まると負け |
| 31〜40 | のれん | 前のマスが空くと、のれんに表示された順で客が出てくる（中の客の色と人数は常に表示） |
| 41〜50 | 予約札 | 札の数だけ皿が下がるまで動けない（残り枚数を表示） |
| 51〜60 | 総仕上げ | 上記の組み合わせ、7×8〜7×9・6色 |

見送り（将来の候補）：相席待ち、カウンター2列。

## 2. 画面構成 【実装済み】

スマホ縦持ちを基準に、片手の親指で全操作が届く配置。横持ち・PC では盤面を中央寄せで拡大する。

```
┌──────────────────────────┐
│ ←      ステージ 12          ↻   │  上部バー（↻ は途中なら確認あり）
├──────────────────────────┤
│  いまの皿   [マグロ] ●●○        │  カウンター（3席）
│  次から →  [玉][鮭][マ][イカ][玉]…│  皿の列（全件・横スクロール、残り枚数表示）
├──────────────────────────┤
│  待ち席  [鮭][  ][  ][  ][  ]    │  K 席
├────────── 出口 ──────────┤
│   ▢ ▢ 鮭 マ 玉                 │
│   玉 柱 鮭 鮭 マ                 │  待合（盤面）：画面の下半分
│   マ 玉 イ 柱 イ                 │  動ける客はわずかに明るく／浮いて見える
│   …                             │
└──────────────────────────┘
```

| 画面 | 内容 |
|---|---|
| タイトル | ゲーム名、「つづきから（ステージ N）」、「ステージを選ぶ」、設定。将来はここでモードを選ぶ |
| ステージ選択 | 番号の格子。クリア済み／挑戦可能（次の1つ）／未解放の3状態。クリア済みはいつでも再挑戦可 |
| プレイ | 上図。動ける客が分かる表示は「ルールの可視化」でありヒントではない（どれを動かすべきかは示さない） |
| クリア | 皿が下がる演出→「次のステージへ」。評価（星など）は無し |
| 失敗 | 「待ち席が満席になりました」／「動かせるお客さんがいません」、「最初からやり直す」「ステージ選択」 |
| 設定 | 演出の速さ（標準／速い／なし）、進行データの消去 |

色覚への配慮：お客さんの胸と皿に、ネタを表す漢字1文字（鮪・玉・胡・鮭・烏・鯖・海・雲）を常に表示し、色だけに頼らない。

演出の方針：
- 客がタップされると、出口までの道を実際にたどって歩き、カウンター／待ち席に跳ねるように座る（200〜400ms）。
- 連鎖時は1段ごとに少し間を置き、段数が増えるほど演出を強める。
- 演出中も次のタップを受け付ける（タップされたら演出を早送りしてから次の手を処理する）。待たせない。

## 3. 進行・保存 【実装済み】

- ステージは 1 から順に解放（クリアで次が開く）。クリアしたかどうかだけを記録する。
- 保存はブラウザの localStorage（キー `omachido.v1`）。アカウント不要。保存できない環境でも遊べる。
- 途中の手順も自動保存し、アプリを閉じても続きから遊べる（ルールが決定的なので、手順を再生すれば同じ局面に戻る）。
- やり込み＝全60ステージクリア。
- 未実装：データの書き出し／読み込み。

## 4. 技術構成 【実装済み】

既存 RPG と同じ **Vite + TypeScript + Preact + Vitest**（無料・ビルド後は静的ファイルのみ・GitHub Pages で配信）。外部サービス・有料 API は使わない。

描画は DOM 要素＋CSS（グラデーション・影・ハイライトで立体感を出した 2D）。絵の素材ファイルは使わず、寿司や客はコードで描く（SVG）。Canvas より、Playwright での UI テストと当たり判定が簡単なため。

### 4.1 共通部分とゲーム固有部分の分離

```
puzzle/
  src/
    core/            共通：ゲームモードの型、ステージ管理、進行、保存、乱数、テーマの型
    modes/
      queue/         Bus Jam型：rules.ts（純粋なルール）、solver.ts、generator.ts、metrics.ts、view/
      （将来）sort/  Sushi Heaven型
    themes/
      sushi/         見た目だけ（ネタの絵・色・名前）
      （将来）bus/
    ui/              タイトル・ステージ選択・設定・共通の結果画面
  stages/            確定したステージデータ（queue.json）
  tools/             ステージ生成（gen-queue.ts）
  tests/             単体・全ステージ検証・自動プレイ（Vitest）
  e2e/               UI テスト（Playwright）
  docs/
```

各モードは共通の型を満たす：

```ts
interface GameMode<Stage, State, Move> {   // src/core/mode.ts
  id: string;
  name: string;
  init(stage: Stage): State;
  legalMoves(state: State): Move[];
  apply(state: State, move: Move): State | null;   // 不正な手は null
  status(state: State): 'playing' | 'cleared' | 'full' | 'stuck';
}
// 途中保存は「手順の配列」で行う（どのモードでも決定的なので共通化できる）
// Bus Jam型の apply は演出用に途中経過（Frame）も返せる
```

ルールは副作用の無い純粋な関数にし、UI・ソルバー・テストがまったく同じルールの実装を使う（表示と検証でルールがずれない）。

## 5. ステージ生成・解法探索・品質保証 【実装済み】（重要）

### 5.1 方針
- **ステージは開発時に生成・検証して固定データにする**（全員が同じ盤面。プレイ中の乱数はゼロ）。
- 生成はシード付き乱数で再現可能にする。ステージを作り直しても同じ結果になる。
- 「開発者が手で解けた」ことを品質の根拠にしない。**全ステージを CI で毎回、完全なソルバーで検証**する。

### 5.2 ソルバー（`src/modes/queue/solver.ts`）
- 深さ優先探索＋局面の記憶（盤面・皿の位置・座っている人数・待ち席の色構成が同じなら同じ局面）。
- 満席になる手は探索しない。合う客と、出番の近い色の客から先に試す。
- 探索量に上限を設け、超えた候補は採用しない。

### 5.3 品質指標と採用基準（`src/modes/queue/specs.ts`）

| 指標 | 意味 | 基準 |
|---|---|---|
| 解けるか | 完全探索でクリア手順が存在する | 必須 |
| 本質的に異なる解法の数 | どの客を待ち席に通したかの組が違う解法の数（手の順番を変えて30回解いて数える） | 1〜2面は1以上、3〜10面は2以上、以降3以上 |
| 序盤の自由度 | 最初の一手のうち、クリア可能なまま進める手の数 | 2以上（1本道の禁止） |
| 難易度 | 素直な打ち手（合う客を優先し、合わなければ満席にならない範囲で無作為）150回の勝率 | ステージごとの目標範囲（1面 90〜100% → 60面 0.6〜10%） |
| 罠の深さ | 素直な打ち手が詰みに入った局面から、実際に負けるまでに打てる最大の手数 | 1〜20面 8手以下、21〜50面 12手以下、51〜60面 16手以下 |
| 参考 | 何も考えない打ち手の勝率、最善手順での待ち席の余裕 | 記録のみ |

生成ツールは設計表の各行について、シードを変えて候補を作り、基準を満たした候補のうち難易度の目標範囲の中央に近いものを採用する。採用時の計測シードをステージデータに記録し、テストで同じ計測を再現して基準を確かめる。

### 5.4 初版60面の計測結果（要約）

- 全60面：クリア可能。序盤の自由度は全面で「どの初手を選んでも勝ち筋に残る」。異なる解法は全面で22通り以上（31通りが数え方の上限）。
- 素直な打ち手の勝率：1〜2面 100% → 10面 41% → 20面 21% → 30面 10% → 50面 5% → 56〜60面 0.7〜2.7%。
- 何も考えない打ち手の勝率：4面以降はほぼ0%（考えないとクリアできない）。
- 罠の深さ：最大16手（57面）。多くは2〜7手。
- 試行錯誤の記録：8×9・7色の盤面は素直な打ち手が一度も勝てず、難しすぎたため、最難関帯は 7×8〜7×9・6色にした。「先を読む打ち手」も試したが勝つか負けるかの両極端で難易度の物差しにならず、採用しなかった。

### 5.5 自動テスト

| 種類 | 内容 | 場所 |
|---|---|---|
| 単体 | 道の判定、着席・待ち席・連鎖、満席・手詰まり、予約札、のれん、データ検証、ソルバーと総当たりの一致、保存、ステージの解放 | `tests/queue.rules.test.ts`, `tests/save.test.ts` |
| 全ステージ検証 | 全面をソルバーで解き、品質基準を再計測して確認 | `tests/queue.stages.test.ts` |
| 全ステージ自動プレイ | 解法をルール本体で再生してクリア／無作為・素直な打ち手で各20回遊び、終局状態と客の数の整合を確認／演出用の途中経過と結果の一致 | 同上 |

## 6. テーマの分離

ルールが知っているのは「色番号」と「マスの種類」だけ。テーマは色番号→見た目（寿司ネタ／バスの色と乗客）、文言（皿／バス、待ち席／駐車場）を割り当てる。将来のバステーマは見た目と文言の差し替えだけで追加できる。
