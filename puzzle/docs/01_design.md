## 1. ゲームルール（Bus Jam型：「おまちどう」）【確定・実装済み】

ルール本体はテーマと無関係（§6）。寿司テーマでは「盤面のお寿司の皿を、カウンターのお客さんの注文どおりに出す」見え方にする。

### 1.1 構成要素

| 要素 | 内容 |
|---|---|
| 盤面 | W×H のマス目。各マスは「空き」「皿」「のれん」のどれか。上辺がカウンター側 |
| 皿 | ネタ（色）を1つ持つ。**真上にしか動けない**ので、各列は皿の山になる |
| お客さん（注文） | 「このネタを n 皿ほしい」。n は 2〜4（1〜10面と21面は3で固定） |
| 行列 | このあとのお客さんの順番と注文。**全員を常に表示** |
| 置き台 | 合わない皿を一時的に置く場所。数 K（3〜6） |

### 1.2 操作と処理（タップのみ）

1. 皿をタップする。**真上のマスがすべて空いている皿**だけ取れる（最上段の皿は常に取れる）。横に回り込むことはできない。
2. 取れる皿は：
   - いまのお客さんの注文と同じネタ → お客さんへ渡す
   - 違う → 置き台へ。**置き台がいっぱいなら取れない**（揺れるだけ。負けにはならない）
3. 注文の皿数がそろうと、お客さんが帰り、次のお客さんが座る。
4. 次のお客さんの注文に合う皿が置き台にあれば、**自動で**渡す（左から順）。これで注文がそろえば、さらに次へ進む——**連鎖**。
5. 皿が抜けたマスは空きになり、その下の皿が取れるようになる。

取れる手（注文に合う皿、置き台に空きがあれば合わない皿も）は少し浮いて明るく表示し、取れない皿は暗く表示する。これはルールの見える化で、どの手が良いかは示さない。

### 1.3 クリアとゲームオーバー

- **クリア**：全員の注文を出し終える。
- **ゲームオーバー（唯一の失敗）**：打てる手が1つも無い（取れる皿がない、または置き台がいっぱいで取れる皿がどれも注文に合わない）。画面には理由（「置き台がいっぱいで、渡せるお皿がありません」／「取れるお皿がありません」）を出す。
- もうクリアできない局面になっても、手が残っている間は知らせない。手数・時間の制限は無い。やり直しは無料・無制限、一手戻すは無い。

### 1.4 考えどころ

- どの列を掘り進めると、次の注文の皿にたどり着けるか（盤面整理）
- 置き台に何を置くか。置いた皿が後のお客さんの注文で一気に連鎖するように（効率・連鎖）
- 行列を先読みし、置き台が残り少ない状況から立て直す（ギリギリからの逆転）

### 1.5 ギミック【実装済み】

すべて見た目で状態が分かるもの。導入面では説明を表示する。

| ステージ | 追加要素 | ルール |
|---|---|---|
| 1〜10 | 基本 | 注文は3皿固定。2色・3×3 から 4色・6×5 まで |
| 11〜20 | 注文の皿数がいろいろ | お客さんごとに 2〜4 皿 |
| 21〜30 | 置き台が少ない | 3〜5 |
| 31〜40 | のれん | 最下段ののれんから、上のマスが空くたびに、表示された順で皿が出てくる |
| 41〜50 | 予約札 | 札の人数だけお客さんが帰るまで取れない（残り人数を表示） |
| 51〜60 | 総仕上げ | 組み合わせ。最大 7×7・6色 |

見送り：柱（上にしか動けないルールでは、柱の下が使えないマスになるだけなので外した。ルール上は残してある）、カウンター2列。

## 2. 画面構成 【実装済み】

スマホ縦持ちを基準に、片手の親指で全操作が届く配置。横持ち・PC では盤面を中央寄せで拡大する。

```
┌──────────────────────────┐
│ ←      ステージ 12          ↻   │  上部バー（↻ は途中なら確認あり）
├──────────────────────────┤
│  (客:鮪 1/3)  [皿][  ][  ]       │  カウンター（いまのお客さんと注文）
│  このあと: 玉×2 鮭×3 鮪×4 …      │  行列（全員・注文の皿数つき）
├──────────────────────────┤
│  置き台  [鮭][  ][  ][  ][  ]    │  K 個
├──────── カウンターへ ────────┤
│   ・ ・ 鮭 鮪 玉                 │
│   玉 鮪 鮭 鮭 鮪                 │  盤面（皿の山）：画面の下半分
│   鮪 玉 烏 胡 烏                 │  取れる皿はわずかに明るく／浮いて見える
│   …                             │
└──────────────────────────┘
```

| 画面 | 内容 |
|---|---|
| タイトル | ゲーム名、「つづきから（ステージ N）」、「ステージを選ぶ」、設定。将来はここでモードを選ぶ |
| ステージ選択 | 番号の格子。クリア済み／挑戦可能（次の1つ）／未解放の3状態。クリア済みはいつでも再挑戦可 |
| プレイ | 上図。動ける客が分かる表示は「ルールの可視化」でありヒントではない（どれを動かすべきかは示さない） |
| クリア | 皿が下がる演出→「次のステージへ」。評価（星など）は無し |
| ゲームオーバー | 理由（置き台がいっぱい／取れる皿が無い）、「最初からやり直す」「ステージ選択」 |
| 設定 | 演出の速さ（標準／速い／なし）、進行データの消去 |

色覚への配慮：皿とお客さんの胸に、ネタを表す漢字1文字（鮪・玉・胡・鮭・烏・鯖・海・雲）を常に表示し、色だけに頼らない。

演出の方針：
- 皿がタップされると、真上に抜けてお客さんの前／置き台へ運ばれる。
- 注文がそろうとお客さんと皿が右へ去り、行列から次のお客さんが進み出る。連鎖時は1段ごとに少し間を置く。
- 演出中も次のタップを受け付ける（タップされたら演出を早送りしてから次の手を処理する）。待たせない。

## 3. 進行・保存 【実装済み】

- ステージは 1 から順に解放（クリアで次が開く）。クリアしたかどうかだけを記録する。
- 保存はブラウザの localStorage（キー `omachido.v1`）。アカウント不要。保存できない環境でも遊べる。
- 途中の手順も自動保存し、アプリを閉じても続きから遊べる（ルールが決定的なので、手順を再生すれば同じ局面に戻る）。
- やり込み＝全60ステージクリア。
- 未実装：データの書き出し／読み込み。

## 4. 技術構成 【実装済み】

既存 RPG と同じ **Vite + TypeScript + Preact + Vitest**（無料・ビルド後は静的ファイルのみ・GitHub Pages で配信）。外部サービス・有料 API は使わない。

描画は DOM 要素＋CSS（グラデーション・影・ハイライトで立体感を出した 2D）。絵の素材ファイルは使わず、寿司や客はコードで描く（SVG）。Canvas より、Playwright での UI テストと当たり判定が簡単なため。

### 4.1 共通部分とゲーム固有部分の分離

```
puzzle/
  src/
    core/            共通：ゲームモードの型、ステージ管理、進行、保存、乱数、テーマの型
    modes/
      queue/         Bus Jam型：rules.ts（純粋なルール）、solver.ts、generator.ts、metrics.ts、view/
      （将来）sort/  Sushi Heaven型
    themes/
      sushi/         見た目だけ（ネタの絵・色・名前）
      （将来）bus/
    ui/              タイトル・ステージ選択・設定・共通の結果画面
  stages/            確定したステージデータ（queue.json）
  tools/             ステージ生成（gen-queue.ts）
  tests/             単体・全ステージ検証・自動プレイ（Vitest）
  e2e/               UI テスト（Playwright）
  docs/
```

各モードは共通の型を満たす：

```ts
interface GameMode<Stage, State, Move> {   // src/core/mode.ts
  id: string;
  name: string;
  init(stage: Stage): State;
  legalMoves(state: State): Move[];
  apply(state: State, move: Move): State | null;   // 不正な手は null
  status(state: State): 'playing' | 'cleared' | 'full' | 'stuck';
}
// 途中保存は「手順の配列」で行う（どのモードでも決定的なので共通化できる）
// Bus Jam型の apply は演出用に途中経過（Frame）も返せる
```

ルールは副作用の無い純粋な関数にし、UI・ソルバー・テストがまったく同じルールの実装を使う（表示と検証でルールがずれない）。

## 5. ステージ生成・解法探索・品質保証 【実装済み】（重要）

### 5.1 方針
- **ステージは開発時に生成・検証して固定データにする**（全員が同じ盤面。プレイ中の乱数はゼロ）。
- 生成はシード付き乱数で再現可能にする。ステージを作り直しても同じ結果になる。
- 「開発者が手で解けた」ことを品質の根拠にしない。**全ステージを CI で毎回、完全なソルバーで検証**する。

### 5.2 ソルバー（`src/modes/queue/solver.ts`）
- 深さ優先探索＋局面の記憶（盤面・注文の位置・渡した皿の数・置き台の色構成が同じなら同じ局面）。
- 注文に合う皿と、出番の近い色の皿から先に試す。
- 探索量に上限を設け、超えた候補は採用しない。

### 5.3 品質指標と採用基準（`src/modes/queue/specs.ts`）

| 指標 | 意味 | 基準 |
|---|---|---|
| 解けるか | 完全探索でクリア手順が存在する | 必須 |
| 本質的に異なる解法の数 | どの皿を置き台に通したかの組が違う解法の数（手の順番を変えて30回解いて数える） | 1〜2面は1以上、3〜10面は2以上、以降3以上 |
| 序盤の自由度 | 最初の一手のうち、クリア可能なまま進める手の数 | 2以上（1本道の禁止） |
| 難易度 | 素直な打ち手（注文に合う皿があればそれを、なければ無作為に置き台へ）150回の勝率 | ステージごとの目標範囲（1面 90〜100% → 50面 1〜20%）。51〜60面は 0%〜 を許す |
| 罠の深さ | 素直な打ち手が詰みに入った局面から、実際にゲームオーバーになるまでに打てる最大の手数 | 1〜20面 8手以下、21〜50面 12手以下、51〜60面 16手以下 |
| 参考 | 何も考えない打ち手の勝率、解法での置き台の余裕 | 記録のみ |

生成ツールは設計表の各行について、シードを変えて候補を作り、基準を満たした候補のうち難易度の目標範囲の中央に近いものを採用する。採用時の計測シードをステージデータに記録し、テストで同じ計測を再現して基準を確かめる。

### 5.4 v0.3（60面）の計測結果（要約）

- 全60面：クリア可能。序盤の自由度は59面で「どの初手を選んでもクリアの可能性が残る」（60面のみ 7手中4手）。異なる解法は全面で6通り以上（3面以降は19通り以上。31通りが数え方の上限）。
- 素直な打ち手の勝率：1面 100% → 10面 34% → 20面 5% → 30面 15% → 40面 6% → 50面 13% → 51〜60面 0〜9%。
- 罠の深さ：最大15手（52・53面）。
- 上にしか動けないルールでは取れる皿が各列の一番上だけになり、大きい盤面は大半が解けない（7×7・6色で約3分の1）。そのため最大の盤面を 7×7 に下げ、置き台を5〜6に増やした。51面以降は「素直に打つだけではほぼ勝てないが、先を読めば必ず解ける」面。

### 5.5 自動テスト

| 種類 | 内容 | 場所 |
|---|---|---|
| 単体 | 取れる皿（真上のみ）、注文・置き台・連鎖、置き台がいっぱいでも合う皿は取れる、ゲームオーバー、予約札、のれん、データ検証、ソルバーと総当たりの一致、保存、ステージの解放 | `tests/queue.rules.test.ts`, `tests/save.test.ts` |
| 全ステージ検証 | 全面をソルバーで解き、品質基準を再計測して確認 | `tests/queue.stages.test.ts` |
| 全ステージ自動プレイ | 解法をルール本体で再生してクリア／無作為・素直な打ち手で各10回遊び、終局状態・皿の数の整合・置き台の上限を確認／演出用の途中経過と結果の一致 | 同上 |

## 6. テーマの分離

ルールが知っているのは「色番号」と「マスの種類」だけ。テーマは色番号→見た目（寿司ネタ／バスの色と乗客）、文言（お客さん／バス、置き台／駐車場）を割り当てる。将来のバステーマは見た目と文言の差し替えだけで追加できる。
