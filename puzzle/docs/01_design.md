## 1. ゲームルール（Bus Jam型：仮称「おあいそ待ち」モード）【提案】

寿司屋のテーマで説明する。ルール本体はテーマと無関係（§6）で、「バス」テーマに差し替えても同じルールで遊べる。

### 1.1 構成要素

| 要素 | 内容 |
|---|---|
| 待合（盤面） | W×H のマス目。各マスは「空き」「客」「柱（通れない）」のどれか。上辺がカウンターへの出口 |
| 客 | ネタの色（=注文）を1つ持つ。各ネタの客数は必ず3の倍数 |
| カウンター | いま握っている皿が1枚。皿には**3席**あり、同じネタの客だけが座れる |
| 皿の列 | これから出る皿の順番。**全件を常に表示** |
| 待ち席 | 合わない客を一時的に座らせる長椅子。席数 K（標準5、難しいステージで4〜3） |

### 1.2 操作と処理（タップのみ）

1. 客をタップする。その客から**上辺の出口まで、空きマスだけを通る上下左右の道**があれば動ける（いちばん上の行の客は常に動ける）。道が無い客は少し揺れるだけで何も起きない。
2. 動ける客は：
   - 注文が**いまの皿と同じ** → カウンターの空席へ座る
   - 違う → 待ち席へ。**待ち席が満席なら動かない**（揺れて戻る。負けにはならない）
3. 皿の3席が埋まると、客が食べ終えて皿が下がり、次の皿が出る。
4. 新しい皿と同じ注文の客が待ち席にいれば、**自動で**カウンターへ移る（左から順）。これで皿が埋まれば、さらに次の皿へ進む——**連鎖**。
5. 客が抜けたマスは空きになり、奥の客の道が開く。

### 1.3 クリアと失敗

- **クリア**：全員が食べ終える（皿の列が空になる）。
- **手詰まり（唯一の失敗）**：クリアしておらず、動かせる客が1人もいない（＝道のある客が全員「合わない注文」で、待ち席が満席）。手数制限・時間制限は無い。
- 手詰まり画面からは「最初からやり直す」（無料・無制限）。

### 1.4 このルールで生まれる考えどころ

- どの客を先に出すと、奥の客の道が開くか（盤面整理）
- 待ち席の何席までなら使ってよいか、何を預けると後の皿で一気に連鎖するか（効率・連鎖）
- 皿の列を先読みし、待ち席が残り1席の状況から立て直す（ギリギリからの逆転）

### 1.5 ギミック（段階的に追加）【提案】

すべて**見た目で状態が分かる**ものに限る。隠し情報・時間で変わるものは採用しない。

| 導入目安 | ギミック | ルール | 狙い |
|---|---|---|---|
| 1〜 | （基本のみ） | 3色→4色、盤面 5×5 から | ルール理解 |
| 11〜 | 柱 | 通れないマス | 道の形を考えさせる |
| 21〜 | 待ち席の削減 | K=4 | 待ち席の管理 |
| 31〜 | のれん（入口） | 決まったマスから、表示された順番で客が出てくる（次の客がのれんに見えている） | 列の先読み |
| 41〜 | 相席待ち | 隣の客がいなくなるまで動けない（札で表示） | 順序の制約 |
| 51〜 | 予約札 | 皿が N 枚出るまで動けない（残り枚数を表示） | 時間差の計画 |
| 後期 | カウンター2列 | 皿が同時に2枚出ていて、どちらにも座れる | 選択肢の拡大 |

各ギミックは導入ステージで「それだけ」を小さな盤面で見せ、数ステージは単独で使ってから組み合わせる。

## 2. 画面構成 【提案】

スマホ縦持ちを基準に、片手の親指で全操作が届く配置。横持ち・PC では盤面を中央寄せで拡大する。

```
┌──────────────────────────┐
│ ←  ステージ 12        ↻ やり直す │  上部バー
├──────────────────────────┤
│  いまの皿   [マグロ] ●●○        │  カウンター（3席）
│  次から →  [玉][鮭][マ][イカ][玉]…│  皿の列（全件・横スクロール、残り枚数表示）
├──────────────────────────┤
│  待ち席  [鮭][  ][  ][  ][  ]    │  K 席
├────────── 出口 ──────────┤
│   ▢ ▢ 鮭 マ 玉                 │
│   玉 柱 鮭 鮭 マ                 │  待合（盤面）：画面の下半分
│   マ 玉 イ 柱 イ                 │  動ける客はわずかに明るく／浮いて見える
│   …                             │
└──────────────────────────┘
```

| 画面 | 内容 |
|---|---|
| タイトル | ゲーム名、「つづきから（ステージ N）」、「ステージを選ぶ」、設定。将来はここでモードを選ぶ |
| ステージ選択 | 番号の格子。クリア済み／挑戦可能（次の1つ）／未解放の3状態。クリア済みはいつでも再挑戦可 |
| プレイ | 上図。動ける客が分かる表示は「ルールの可視化」でありヒントではない（どれを動かすべきかは示さない） |
| クリア | 皿が下がる演出→「次のステージへ」。評価（星など）は無し |
| 手詰まり | 盤面を残したまま暗くし、「最初からやり直す」「ステージ選択へ」 |
| 設定 | 演出の速さ（標準／速い）、色覚サポート（ネタごとに形と文字でも区別：常時オン推奨）、データの消去 |

演出の方針：
- 客がタップされると、出口までの道を実際にたどって歩き、カウンター／待ち席に跳ねるように座る（200〜400ms）。
- 連鎖時は1段ごとに少し間を置き、段数が増えるほど演出を強める。
- 演出中も次のタップを受け付ける（入力は即時に論理へ反映し、見た目が追いかける）。待たせない。

## 3. 進行・保存 【提案】

- ステージは 1 から順に解放（クリアで次が開く）。クリアしたかどうかだけを記録する。
- 保存はブラウザの localStorage（進行は数百バイト程度）。アカウント不要。データの書き出し／読み込み（JSON）を設定に置く。
- 途中の盤面も自動保存し、アプリを閉じても続きから遊べる。
- やり込み＝全ステージクリア。初期は 60 ステージ程度を目標（Q5）。

## 4. 技術構成 【提案】

既存 RPG と同じ **Vite + TypeScript + Preact + Vitest**（無料・ビルド後は静的ファイルのみ・GitHub Pages で配信）。外部サービス・有料 API は使わない。

描画は DOM 要素＋CSS（グラデーション・影・ハイライトで立体感を出した 2D）。絵の素材ファイルは使わず、寿司や客はコードで描く（SVG）。Canvas より、Playwright での UI テストと当たり判定が簡単なため。

### 4.1 共通部分とゲーム固有部分の分離

```
puzzle/
  src/
    core/            共通：ゲームモードの型、ステージ管理、進行、保存、乱数、テーマの型
    modes/
      queue/         Bus Jam型：rules.ts（純粋なルール）、solver.ts、generator.ts、metrics.ts、view/
      （将来）sort/  Sushi Heaven型
    themes/
      sushi/         見た目だけ（ネタの絵・色・名前）
      （将来）bus/
    ui/              タイトル・ステージ選択・設定・共通の結果画面
  stages/            確定したステージデータ（モードごと）
  tools/             ステージ生成・検証のコマンド
  tests/             単体・全ステージ検証・自動プレイ・UI（Playwright）
  docs/
```

各モードは共通の型を満たす：

```ts
interface GameMode<Stage, State, Move> {
  id: string;
  init(stage: Stage): State;
  legalMoves(state: State): Move[];
  apply(state: State, move: Move): { state: State; events: GameEvent[] }; // events は演出用
  status(state: State): 'playing' | 'cleared' | 'stuck';
  serialize(state: State): string;   // 途中保存
  View: Component;                    // モード固有の盤面表示
}
```

ルールは副作用の無い純粋な関数にし、UI・ソルバー・テストがまったく同じルールの実装を使う（表示と検証でルールがずれない）。

## 5. ステージ生成・解法探索・品質保証 【提案】（重要）

### 5.1 方針
- **ステージは開発時に生成・検証して固定データにする**（全員が同じ盤面。プレイ中の乱数はゼロ）。
- 生成はシード付き乱数で再現可能にする。ステージを作り直しても同じ結果になる。
- 「開発者が手で解けた」ことを品質の根拠にしない。**全ステージを CI で毎回、完全なソルバーで検証**する。

### 5.2 ソルバー
- 深さ優先探索＋局面の記憶（取り除いた客の集合・皿の位置・待ち席の中身で同一局面を判定）。
- 動かす順番を入れ替えても結果が同じ手（互いに道に影響しない、待ち席を使わない着席など）は1通りに絞る（半順序による削減）。
- 出力：クリア可能か、手順の例、下記の指標。

### 5.3 品質指標（ステージを採用する基準）

| 指標 | 意味 | 用途 |
|---|---|---|
| 解けるか | 完全探索でクリア手順が存在 | 必須 |
| 勝ち筋の数 | 本質的に異なる（順番の入れ替えだけではない）クリア手順の数 | 「複数の解法」の保証：通常ステージは一定数以上 |
| 序盤の自由度 | 最初の数手で、クリア可能なまま選べる手の数 | 1本道の排除 |
| 罠の深さ | 「その時点では自然に見える手」から、何手後に詰みが確定するか | 理不尽さの上限：深すぎる罠は不採用 |
| 素直な打ち手の勝率 | 「合う客を優先し、待ち席を残す」程度の簡単な方針で打つ自動プレイヤーの勝率 | 難易度の目安（序盤は高く、後半は低く） |
| 1手先読みの勝率 | 「直後に詰む手だけは避ける」自動プレイヤーの勝率 | 運だけでは勝てないこと（低すぎず、高すぎず） |
| 最小の待ち席余裕 | 最善手順でも待ち席が何席残るか | 「ギリギリ」の演出量 |

難易度帯ごとに合格範囲を決め、候補を大量生成→検証→合格したものを難易度順に並べる。高難易度帯は勝ち筋が少なく罠が深いものを許すが、「罠の深さ」には上限を設ける（数手先を読めば必ず避けられる）。

### 5.4 試作での確認（Python、使い捨て）

客を盤面いっぱいにランダム配置、皿の順番もランダム、各20〜30盤面：

| 盤面 | 色 | 待ち席 | 解けた割合 | 適当に打つ | 合う客優先 | 探索時間（解けた盤面） |
|---|---|---|---|---|---|---|
| 5×6 | 3 | 5 | 20/20 | 69% | 76% | 一瞬 |
| 6×6 | 4 | 5 | 20/20 | 24% | 30% | 0.01秒 |
| 7×8 | 5 | 5 | 20/20 | 20% | 27% | 0.04秒 |
| 7×8 | 6 | 4 | — | 0% | 0% | — |

分かったこと：
- 単純な配置でも「考えないと勝てない」程度の深さはある（ルールとして成立している）。
- 盤面が大きく、**解けない**盤面では素朴な完全探索が重くなる（8×9 で数分以上）。→ §5.2 の削減と、盤面サイズの上限（当面 8×9 程度）で対応する。実装後に計測して確定する。

### 5.5 自動テスト

| 種類 | 内容 |
|---|---|
| 単体 | 道の判定、着席・待ち席・連鎖、手詰まり判定、各ギミック、保存と読み込み、進行の解放 |
| 全ステージ検証 | 全ステージをソルバーで解き、指標が合格範囲内であることを確認 |
| 全ステージ自動プレイ | ソルバーの手順をルール本体で再生してクリアになること／わざと詰ませて手詰まりになること |
| UI | Playwright（スマホ画面サイズ）で、タップ→クリア→次のステージ、手詰まり→やり直し、途中保存からの再開、文字や要素のはみ出し、タップ領域の大きさ（44px 以上） |
| 回帰 | 上記を GitHub Actions で push ごとに実行（失敗したら公開しない） |

## 6. テーマの分離

ルールが知っているのは「色番号」と「マスの種類」だけ。テーマは色番号→見た目（寿司ネタ／バスの色と乗客）、文言（皿／バス、待ち席／駐車場）を割り当てる。将来のバステーマは見た目と文言の差し替えだけで追加できる。
